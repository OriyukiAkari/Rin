# Rin v1.1 architecture

## Goal

v1.1 keeps Rin as one deployable product while making each runtime and shared boundary
explicit. It consolidates duplicated contracts and configuration, and splits modules that
mixed unrelated responsibilities.

## Runtime topology

```text
Browser
  -> Cloudflare Pages (React/Vite static frontend)
       -> Pages Function route gate
            -> RIN_API service binding
                 -> Cloudflare Worker (Hono API, RSS, scheduled and queue handlers)
                      -> D1 (relational data and database cache)
                      -> R2 (objects and optional S3-compatible cache)
                      -> Queue / Workers AI when configured
```

Pages owns browser delivery and SPA fallback. Only `/api/*`, root feed routes, and dynamic
favicon routes invoke the Pages Function. The function forwards the original request to the
Worker through `RIN_API`, preserving the Pages origin and HttpOnly cookie behavior. The Worker
does not host `dist/client` and returns 404 for unrelated paths.

## Repository boundaries

- `client/`: the React application and app-specific composition.
- `pages/`: the thin Pages Functions gateway and generated Pages Wrangler configuration.
- `server/`: the Worker application, runtime event adapters, business services, and D1 schema.
- `packages/api/`: transport-facing request/response contracts and canonical API paths.
- `packages/config/`: config registry, defaults, normalization, scopes, and safe wrapper.
- `packages/ui/`: reusable React primitives without client state or routing dependencies.
- `cli/`: the single operational entrypoint for development, migration, deployment, and release.

These are product boundaries, not a generic framework hierarchy. Renaming them to `apps/*` or
adding empty `core` packages is deferred until it would improve the dependency graph.

## Consolidations completed in v1.1

- Runtime service creation is centralized in `server/src/core/runtime-services.ts` for fetch,
  queue, and scheduled events.
- Configuration keys, defaults, valid layout values, normalization, scope, and sensitivity are
  defined once in `@rin/config`.
- API paths and response contracts are centralized in `@rin/api`; the client transport is split
  by content, community, account, configuration, and storage domains behind one facade.
- Shared UI consumers import `@rin/ui` directly; obsolete one-line client wrappers are removed.
- Search and WordPress import are separated from the feed service; parsing helpers have their
  own module.
- Article comments and settings state orchestration are separated from page rendering.
- The CLI deploys the Worker and Pages independently, creates the Pages project when needed,
  and connects them with a service binding.

## Deliberately separate concerns

- Pages and Worker deploy independently even though `bun run deploy` orchestrates both.
- Browser-safe client config and sensitive server config share a registry but remain separate
  scopes and API views.
- D1 is authoritative for relational application state; R2 remains object storage. Neither is
  hidden behind an artificial universal repository abstraction.
- App-specific components stay in `client`; only state-free primitives belong in `@rin/ui`.
- ShokaX remains untouched and will be evaluated in a later version.

## Operational entrypoints

```bash
bun run dev             # Vite frontend plus local Worker, API proxied by Vite
bun run check           # all workspace TypeScript checks
bun run test            # complete test suite
bun run build           # Pages frontend plus Worker dry-run bundle
bun run deploy          # Worker, migrations/secrets, then Pages
bun run deploy:server   # Worker only
bun run deploy:client   # Pages only, bound to WORKER_NAME
```

Deployment resource names use `WORKER_NAME`, `PAGES_PROJECT_NAME` (with `PAGES_NAME` retained as
a compatibility alias), `DB_NAME`, `TASK_QUEUE_NAME`, and `R2_BUCKET_NAME`.
